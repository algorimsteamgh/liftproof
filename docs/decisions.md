# Build decisions

Defaults picked to start building where the PRD and Technical Spec leave a choice open.
Each can be revisited; the ones marked *reversible* cost little to change.

| # | Decision | Default chosen | Why | Reversible |
|---|---|---|---|---|
| 1 | Language | Python 3.12 | The database reconciliation is where the product lives or dies; spec section 2 | Costly |
| 2 | First database engine | PostgreSQL (source and target) | Most common target, and a full test server is easy in CI. MySQL, SQL Server and Oracle follow as adapters | Yes |
| 3 | Package and CLI name | package `liftproof`, commands `liftproof` and `mvt` | Project is called Liftproof; spec uses `mvt`. Both entry points work | Yes |
| 4 | Row hash grouping | per column digest, groups of 32 columns | Resolves the ambiguous 1000 byte rule; see canonical-v1.md | Canonical version bump |
| 5 | NULL encoding | own frame `-1 0x1F` | The draft `\N` collides with the string `\N` | Canonical version bump |
| 6 | Baseline contents | per bucket aggregates only | Keeps baselines small; row level drill-down needs the source readable at validate time, and the report says so when it is not | Yes |
| 7 | Verdict | failed on any difference of severity 3 or more, or an error; passed with differences on low severity differences or anything not checked or partial; else passed | The spec defines the three verdicts but no rule | Yes |
| 8 | Read only check in doctor | inspect grants and superuser, never attempt a write | A write attempt against production takes locks and fires triggers; DDL auto commits on MySQL and Oracle | Yes |
| 9 | Values in reports | hidden by default; `--show-values` or `show_values: true` | The report is an egress path (spec 15) | Yes |
| 10 | AWS keys in the environment | warn, do not refuse | They are part of the default provider chain (AWSAPI-005); database passwords in the environment are refused | Yes |
| 11 | Credentials when no `secret_arn` is set | connect without a password (for local development and IAM auth later) | Never from a file or environment variable | Yes |
| 12 | Infrastructure | Terraform modules for the customer deployment and the Algorims build account; Packer AMI on Ubuntu 24.04 LTS (changed from Amazon Linux 2023 on 2026-10-06: Playwright supports Ubuntu and installs Chromium with its libraries in one step; Amazon Linux is not a Playwright platform) | The spec names CloudFormation and Terraform; Terraform first, CloudFormation for the Marketplace listing next | Yes |
| 13 | Second database engine | MySQL 8.0 and later (Aurora MySQL 3), via PyMySQL | The most common lift and shift engine, a pure Python driver, and a real cross engine test against PostgreSQL. Oracle and SQL Server follow | Yes |
| 14 | MySQL driver version | PyMySQL below 1.2 | PyMySQL 1.2.3 fails the full `caching_sha2_password` login exchange; lift the cap once fixed upstream | Yes |
| 15 | Schema names across engines | `database.schema_map`, defaulting to the source home schema mapped onto the target's (MySQL `shop` to PostgreSQL `public`) | In MySQL a schema is the database; a migration usually renames it | Yes |
| 16 | MySQL replication position | GTID set (or binlog file and position) read immediately after the snapshot opens, recorded with `exact: false` | MySQL does not expose the position of a consistent snapshot atomically; the alternative, a global read lock, is not acceptable on a production source | Yes |
| 17 | Response bodies at record time | default deny: kept only for `web.capture_bodies` URL patterns; every other body is a SHA-256 and a JSON shape | Spec 5: production bodies in the bucket indefinitely is the sentence that loses the deal. Shape comparison still catches added and missing fields | Yes |
| 18 | Which fields are sensitive | password inputs, any element with `data-liftproof-sensitive`, and names matching pass, secret, token, otp or pin | Errs towards redacting; the value is swapped for a random token in the recorder process and scrubbed from URLs, request bodies and page snapshots | Yes |
| 19 | "The region the step touched" | the nearest form, dialog, table, section, article or main around the element, else the page; compared as accessible tree text | Spec 7 asks for the region but does not define it; these are the elements that bound what a step can change | Yes |
| 20 | Waiting at replay | the requests the step made when recorded, then the page load, then no DOM change for 150 ms; step timeout 15 s; 3 attempts per step, 2 per journey that changes state | Conditions, not sleeps (spec 6). The DOM quiet period stops a snapshot racing the page's own rendering script | Yes |
| 21 | Journey with an unbound redaction token | not replayed; reported as not run, so coverage drops; `doctor` lists it beforehand | Replaying without the real secret would fail at login and read as a migration defect | Yes |
| 22 | API calls during recording and replay | fetched through a Playwright route so the body is held before the page sees it | A page that navigates straight after an API call discards that body before it can be read | Yes |
| 23 | Third database engine | Oracle 19c and later (RDS for Oracle), via python-oracledb in thin mode | The largest legacy source estate; thin mode needs no Oracle client on the image. SQL Server follows | Yes |
| 24 | Oracle snapshot and position | One `SET TRANSACTION READ ONLY` transaction; the SCN read right after it begins, recorded with `exact: false`, or unknown without `SELECT` on `V$DATABASE` | Oracle answers every query in a read only transaction as of its start; `AS OF SCN` flashback queries need undo retention the source may not have | Yes |
| 25 | Integer against decimal columns | Planned together as decimal instead of a type change | Oracle `NUMBER` keys move to `bigint`; the renderings agree for whole numbers, so excluding the column would hide real differences | Yes |
| 26 | File content hash | SHA-256, streamed; files paired by relative path, with an optional regex path map and case folding | Files never need the cross engine MD5 of canonical v1.0, and SHA-256 works on a FIPS host. Windows shares moving to S3 change case and folders | Yes |
| 27 | Document types compared as text | PDF (pypdf, no system libraries), JSON (keys sorted), CSV, TSV and pipe delimited (row and column), and plain text types; up to 64 MB per file | Spec 23 leaves the list open and names PDF first. A pure Python reader keeps the AMI free of extra packages | Yes |
| 28 | Severity of file findings | missing in target: high; different text or unreadable type: high; only in target: medium; same text, different bytes: low; unreadable or symbolic link: not checked | Spec 10: a byte difference with identical text ranks below a real difference. A symbolic link is never followed, because it can leave the tree | Yes |
| 29 | Order inside `validate` | reconcile, then files, then replay | Replay creates data and generated files on the target; comparing after it would report them | Yes |
| 30 | Overlapping runs of one project | refused by a run lock: in S3, a conditional put (If-None-Match) with a 15 minute lease renewed while the run lasts and taken over with a conditional put once expired; on a local store, a kernel file lock | Spec 14: runs of one project never overlap. The scheduler, the CLI and SSM Run Command are separate processes, so only the store can arbitrate; S3 conditional writes need no DynamoDB table | Yes |
| 31 | A scheduled run that would overlap | skipped, and the skip is a run: a report with a high severity error finding and a `ScheduledRunSkipped` CloudWatch metric (namespace Liftproof; dimensions Deployment, which the deployment's alarm watches, and Deployment plus Project); exit code 2 | A skip seen only in a log goes unnoticed for weeks. A run started by hand is refused with exit code 2 and writes nothing | Yes |
| 32 | Scheduler | `mvt-scheduler.service` reads `schedules:` from every project file; five field cron, wall clock in a named time zone; each run is its own process; runs missed while it was down are not caught up, the latest missed one fires once | Customers with richer needs drive runs from their own pipeline through SSM Run Command (F11). No new dependency for cron parsing | Yes |
| 33 | SSM document modes | validate, reconcile, files, replay, smoke, baseline and doctor, with `journeys` and `sets` parameters restricted by pattern | Every pipeline stage the CLI has can be called without a shell on the instance; the patterns keep parameters out of the shell | Yes |
| 34 | Fourth database engine | SQL Server 2016 and later (RDS for SQL Server, Azure SQL), via python-tds, a pure Python driver, with pyOpenSSL for TLS | No ODBC driver or Microsoft package repository on the image, as with Oracle thin mode. HASHBYTES has no input limit from 2016 | Yes |
| 35 | SQL Server snapshot | A SNAPSHOT isolation transaction, position `@@DBTS` recorded as `exact: false`. Without ALLOW_SNAPSHOT_ISOLATION the source is read under READ COMMITTED, the baseline records `consistent: false`, and doctor fails the check | Turning snapshot isolation on is the DBA's decision (it adds version store load in tempdb); a baseline must not silently claim consistency | Yes |
| 36 | SQL Server TLS | `verify-ca` or `verify-full` with a CA bundle; `require` (encrypt without checking) is refused | The driver only encrypts with a CA bundle. A self signed server certificate can be its own bundle | Yes |
| 37 | CloudFormation template for the Marketplace listing | One template, `infra/cloudformation/liftproof.yaml`, written by hand to mirror `modules/liftproof`; a test compares the inputs, Run Command document, IAM statements, endpoints and instance settings of the two | Spec 3 offers both. Generating one from the other (cdktf, former2) would add a toolchain to the release path; a parity test catches drift with none | Yes |
| 38 | Database egress in the template | Four fixed slots (CIDR and port), an empty CIDR skips the slot; one application port for a list of CIDRs | CloudFormation has no loop over a map, and a Marketplace form cannot take a list of objects. Four covers source, target and a replica each side | Yes |
| 39 | Lookups the template needs | A small Lambda custom resource returns the VPC CIDR (endpoint security group) and the Region's S3 prefix list ID (S3 egress rule); read only EC2 permissions, runs outside the VPC so it needs no extra endpoint, logs to its own log group | Terraform reads both with data sources; CloudFormation has no equivalent | Yes |
| 40 | AMI in the template | `ImageId` is an SSM parameter type defaulting to the Marketplace public parameter for the product, so each stack launches the latest listed version | The ID differs per Region and per version; a mapping would have to be edited on every release | Yes |
| 41 | Rebaseline | `liftproof rebaseline` takes a baseline of the target with the baseline code path (one snapshot, per table checkpoints, `--resume`, `--tables`); the manifest records `side: target`; `--baseline latest-target` selects the newest one and `latest` stays the newest source baseline | Spec 14 and the command table: regression after cutover compares target to target. Two names keep a pipeline written before cutover from silently changing what it compares against | Yes |
| 42 | What a run against a target baseline reads | the target only, never the source; differences down to the bucket, with a not checked finding saying rows cannot be named | The source may be decommissioned, and reading it would compare against something other than the accepted target. A baseline holds aggregates and the target's past state cannot be re-read | Yes |
| 43 | Where the `latest` markers live | in the store next to the baselines as well as on the instance; the store copy wins | A replacement instance pointed at the same bucket still resolves `latest` and `latest-target` (spec 3: nothing irreplaceable on the instance) | Yes |
| 44 | What a support bundle holds | environment (product, canonical, Python, OS and package versions; instance settings), the project's shape (engines, endpoints, secret ARNs, rules, schedules), the run's report and findings, per object results, the baseline manifest and the run's log lines; optionally doctor's checks. Never the HTML report, recordings, response bodies or file contents | Spec 13: the only diagnostic surface on a Customer Deployed product. Each item answers a question support would otherwise ask by email | Yes |
| 45 | Redaction in a support bundle | `expected`, `actual`, database locators (they name key values) and value bearing detail fields (key, source, target, value, values) become `[redacted]`, even when the run had `show_values` on; logs scrubbed again | A bundle leaves the customer's account by design, so it must be safe to send without review. Comparators keep values out of summaries, so summaries stay | Yes |
| 46 | Where the bundle goes | a zip under the work directory and the same file in the store under `support/`; also a mode of the Run Command document | An operator with no shell on the instance can make one from a pipeline or the console and download it from S3 | Yes |
| 47 | KPI suite | `pytest -m perf` (tests/perf), one test per PRD N8 threshold plus a large table memory check; called by the release workflow before the AMI is built and on pull requests touching adapters, reconcile, web or report; results kept as `perf-results.json` with the release evidence. KPI 5 (launch to first journey) is timed by hand per release (docs/kpis.md) | N9 makes all five a release gate (spec 19: one named test per threshold, not just throughput) | Yes |
| 48 | Replay KPI conditions | sample checkout journey, 150 ms server latency, 60 replays, worst first attempt ratio of the whole journey's wall clock (recording: first navigation to last settled step; replay: the same span of the attempt). Step timings in the report are measured the same way on both sides: from the action to the end of the last request it caused | Against a local server with no latency the ratio measures only the fixed waits (DOM quiet period); a real application answers across a network. The first version divided replay time including finding and filling fields by recorded time counting only network, so the tool's own work counted against the target: 2.56 on a CI runner for a journey that replays in about the time it was recorded | Yes |
| 49 | Source and target hashed at once | the two bucket aggregate queries run concurrently, each on its own connection | Halves the wall time per table; each database's own load is unchanged, which is what spec 9.15 protects | Yes |
| 50 | Drill-down one bucket at a time | `bucket_rows` yields one bucket's keys and hashes at a time, both sides in step (PostgreSQL in one ordered pass on a server side cursor; other engines one query per bucket by default); only the rows the report can show are kept | Spec 17: nothing loads a table into memory. 13 mismatched buckets of a million row table took 565 MB before, 52 MB after | Yes |
| 51 | Replication position check | `database.replication`: `slot` (a logical slot on a PostgreSQL source, whoever consumes it, AWS DMS included; read on the source) or `subscription` (PostgreSQL logical replication; read on the target), with `wait_seconds` to wait for it to catch up. The reference is the source baseline's position, or the live source's position at the start of the run. Behind: every table not_checked with "replication behind the baseline point", never a difference. The result is in the report's range block; with no method it says "unverified" | Spec 9.2 and 18. These two cover the PostgreSQL sources; MySQL (GTID), Oracle (SCN) and SQL Server (LSN) checks are added to those adapters after their PRs merge. Not run against a target baseline, whose reference is the target itself | Yes |
| 52 | Row ignore rules | An ignore rule can leave out rows instead of a table or column: `where` (both sides) or `source_where` / `target_where` (one side each, in that side's own dialect). Each side hashes, counts and computes float statistics over `WHERE (predicate) IS NOT TRUE`, so a row whose predicate is NULL is still compared rather than silently dropped. Rules on one table are ORed. Every table with a row rule gets a notice naming the rule and both predicates, and a baseline records its filter and is reused only under the same one. A predicate is one SQL condition: `;` and comments are refused, and so is a rule naming a column and rows at once. Predicates run as the read only database user inside the read only snapshot, so a predicate cannot change data. Built for PostgreSQL; an engine without it reports the table as not checked rather than comparing rows it was told to leave out. |
| 53 | Sampled reconciliation | `database.sampling` (`above_rows`, `percent`, optional `seed`): a table with more rows than `above_rows` compares `percent` of its buckets, chosen at random per table from a run seed (recorded in the report, so a rerun with that seed compares the same buckets). Every sampled table gets a not checked finding giving the buckets compared and the share of rows they hold, the HTML report lists sampled tables and tags them in the table list, and the verdict can therefore never be a plain pass. Row counts, the circuit breaker and drill-down work on the sampled buckets; float statistics stay whole table. On PostgreSQL the bucket test runs in the scan, so rows outside the sample are never row hashed (a 1 million row table at 10 % hashes in about a quarter of the time; the key is still hashed for every row). An engine without it compares in full and says so. Baselines are always full, and a sampled run against one uses the same buckets of it | Spec 9.18: we never present a sampled result as a full one. A seed per table keeps tables independent; a recorded seed makes a sampled result reproducible for an auditor | Yes |
| 54 | Parallel journeys | `web.parallel_journeys` (1 to 8, default 1). Above 1, that many workers each run their own Playwright driver and browser and take journeys from a shared queue; every journey still gets a fresh context and its steps run in recorded order; results keep the journeys' order. The report's range block records `journeys_in_parallel` and `parallel_workers` | Spec 6: sequential is the safe default when journeys share data, parallel is an opt in the customer confirms and the report shows. Playwright's sync API is per thread, so one browser cannot be shared across workers. 8 bounds the browsers on one instance | Yes |
| 55 | Parallel database workers | `database.workers` (1 to 8, default 1): that many tables are reconciled or baselined at once, each worker on its own connections, results kept in table order. Workers of a baseline import the snapshot the first connection exported (`SET TRANSACTION SNAPSHOT`), so the baseline is still the hash of one state of the database. The table level circuit breaker counts results as they finish. The rows per second cap applies per connection, so N workers can read N times the rows. An engine without it runs one table at a time and says so. Measured: 8 tables of 200,000 rows, 4 workers, 13.7 s against 25.7 s for one, on a 4 CPU host serving both databases | Spec 9.1: eight workers over ninety minutes against a live source is the hash of a state the database never was, unless they share a snapshot. Spec 9.15: concurrency multiplies source load, so the default is the conservative 1 and 8 is the ceiling | Yes |
| 56 | Row rules and sampling on every engine | MySQL, Oracle and SQL Server apply row ignore rules and sampling as PostgreSQL does: the predicate runs inside the engine and a row is kept unless it is true (`IS NOT TRUE` on MySQL; `CASE WHEN (...) THEN 1 ELSE 0 END = 0` on Oracle and SQL Server, which have no boolean expressions); the sample's bucket test sits on the hash query, and rows read application side (non-ASCII text) skip buckets outside the sample | One behaviour, whichever engines a migration has. A rule written for one dialect goes in `source_where` or `target_where` | Yes |
| 57 | Workers on every engine | Reconcile workers open more connections on any engine. A baseline uses workers only when every connection reads one state of the database: PostgreSQL through an exported snapshot, Oracle through `DBMS_FLASHBACK` at the snapshot's SCN (which also makes the recorded position exact; needs EXECUTE on DBMS_FLASHBACK). MySQL and SQL Server cannot hand a snapshot to another connection, so their baselines run one table at a time and say so | A baseline must stay the hash of one state of the database (spec 9.1). Oracle refuses flashback to before a table's last DDL (ORA-01466): a table altered during a baseline fails it rather than mixing states | Yes |
| 58 | Replication check on every engine | Two more methods. `replica`: MySQL replication, read on a MySQL target; a GTID reference must be a subset of the target's executed set, a binlog reference at or before the replica channel's executed position (`name` is the channel, empty for the default; needs REPLICATION CLIENT). `dms`: an AWS DMS task, any source and target engine, read on the target from the task's `awsdms_status` control table (StatusTableEnabled; `control_schema` when the task sets ControlSchema). DMS reports source commit times, not positions, so it has caught up when it has applied a commit at or after the reference snapshot's time, or has read past that time with nothing pending (an idle source). Times in the control table are read as UTC | DMS is the usual route into RDS and Aurora from Oracle and SQL Server, and its control table is the one place the target can say how far it has got. The idle source rule avoids waiting forever when nothing changes after cutover | Yes |
| 59 | Correlation transform chains | A correlation carries `transforms` (decoding applied after extraction: `url_decode`, `base64_decode`, `base64url_decode`, up to two deep) and `encodings` (other forms a later step uses: `url`, `url_plus`, `base64`, `base64url`). Recording finds both: a value is tried as sent first, its decoded forms only when it is not reused as sent. Replay substitutes every form; the comparator masks every form, the encoded one the server sent included. An engineer can edit both lists in the journey file; unknown names refuse to load | Ids that travel base64 in a tracking link or URL encoded in a form were not carried over, so the replayed step used the recorded value | Yes |
| 60 | Replay windows | Around every replay the target's watermark is read for each table the journeys write (`record --writes`): the largest value of `database.replay_watermarks.<table>`, else of a single column primary key that only grows (integer, exact number or timestamp). Rows in (before, after] are the replay's; the windows are kept in the store (`replay/windows.json`) and every later reconciliation leaves them out on the target side as a row rule naming the replay run. `--include-replay-rows` compares them. Against a target baseline only the windows recorded after it apply | validate reconciles before it replays, but a scheduled replay followed by a reconcile reported the orders the journeys placed as extra rows | Yes |
| 61 | Replay window limits | Rows other users create on the target inside the window are left out too; changes a replay makes to existing rows are not windows and still show as differences; a table without a growing column gets a notice and no window | A replay window is seconds long. Telling a replay's update from a user's needs the application's own audit data | Yes |
| 62 | Oracle GoldenGate check | `goldengate`, read on the target of any engine: `name` is the Replicat, with `checkpoint_table` (its CHECKPOINTTABLE), `heartbeat_table` (GG_HEARTBEAT from ADD HEARTBEATTABLE) or both. Caught up when the checkpoint table's LOG_CMPLT_CSN is at or past the reference SCN (Oracle sources), or when a heartbeat the Replicat applied was created at or after the reference snapshot time (any source, and an idle one). The threads of a coordinated or parallel Replicat (the name plus three digits) all count, the slowest deciding. Heartbeat times are read as UTC | The checkpoint table is the exact answer for an Oracle source, but its CSN stops moving when the source is idle and is not an SCN for other source engines; the heartbeat, about once a minute, covers both, so `wait_seconds` should exceed the heartbeat frequency | Yes |
| 63 | SQL Server availability group check | `availability_group`, read on the source (the primary): `name` is the target's replica, or the target's group in a distributed availability group. The reference is the primary's own last commit LSN, read as the snapshot opens (recorded as `commit_lsn`, `exact: false`); caught up when the target replica's last redone commit LSN is at or past it. Needs VIEW SERVER STATE; without it, or outside an availability group, the check is unverified, never behind. Transactional replication is not covered (the subscriber cannot tell an idle publisher from a stalled one); use DMS or an availability group | A distributed availability group is AWS's recommended route for SQL Server onto EC2. Commit LSNs only move with commits, so an idle primary and a synchronised replica show the same one | Yes |
| 64 | Live source position on every engine | Without a baseline, the reference is the live source's position at the start of the run on every engine (it was PostgreSQL only): the SCN on Oracle, the GTID set or binlog position on MySQL, @@DBTS and the availability group commit LSN on SQL Server, each with the time it was read, which `dms` and `goldengate` need | A replication check without a baseline was unverified on these engines | Yes |
| 65 | Web UI | `liftproof ui` (service `mvt-ui`, port 8080 on 127.0.0.1 only, reached through Session Manager port forwarding) lists projects, runs and schedules, opens reports, starts runs, and finishes journeys (binds secrets by ARN, confirms correlations). Everything it does it does by running the CLI as its own process, as the scheduler and the run document do; a run's options are checked against what that command takes, and nothing typed reaches the command line except names. Show values and custom report templates are left to the CLI. Recording needs a browser window, so it stays a CLI step on a machine with a display; the journey then appears in the UI | Spec 4 and 23: the CLI is the product and the UI a convenience over it, so nothing works only in the UI | Yes |
| 66 | Web UI sign in | Port forwarding carries no identity, so the UI signs people in with a one time link from `liftproof ui-login`, also the `ui-login` mode of the run document: one use, within ten minutes, only its hash kept on disk; it starts a 12 hour session cookie (HttpOnly, SameSite Strict). Requests naming any host but 127.0.0.1 or localhost on the UI's port are refused (DNS rebinding); forms carry a value derived from the session; pages send a strict Content Security Policy. Who ran a run is the name people give the UI, recorded as ui:name: what they say, not a verified identity | The operator role already holds port forwarding and the run document, so a link from the run document needs no new permission, and the link in the command's output is spent or out of date by the time anyone else could read it | Yes |
| 67 | Instance settings | `/etc/mvt/config.yaml` is root:mvt 0640, readable by every product process (all run as `mvt`). When it exists but cannot be read, a run stops with a configuration error naming `sudo -u mvt` instead of carrying on without it | Carrying on would quietly drop the deployment's bucket, KMS key, report lock and alarm dimension | Yes |
| 68 | Default CA for database TLS | The AMI ships the Amazon RDS CA bundle (kept in the repository) and joins it with the system CAs in `/opt/mvt/certs/ca-bundle.pem`, which every engine uses under `verify-ca` and `verify-full` when the project names no `sslrootcert`. MySQL's verifying modes always pass an SSL context, never PyMySQL's dict form, which switches checking off when no CA is given | RDS and publicly signed endpoints verify with no setting; a private CA still goes in `sslrootcert` | Yes |
| 69 | Release job identity | The release job runs without a GitHub environment, so its OIDC subject is the tag ref the release role trusts; release settings are repository variables. Every workflow step runs as `bash -eo pipefail`. The build account has EBS encryption by default off, so the AMI's snapshot stays unencrypted for Marketplace | An environment subject would be refused by the role; without pipefail a piped `pip-audit` never fails; default encryption would encrypt the AMI with a key that cannot be shared | Yes |
| 70 | Release gates | A `v*` tag builds only when the tagged commit is on `main`, `__version__` equals the tag, and the functional suite, the dependency audit and the KPI suite pass on that commit. The image's installed packages are audited again inside the build (fails on any known vulnerability) and that audit, with the Playwright browser builds, is kept with the release evidence | OPE-004 asks for the suite before anything is released, B6 for scanning what actually ships. No scanner covers Playwright's Chromium, so its build is recorded instead and moves with each Playwright update | Yes |
| 71 | Product logs to CloudWatch | `/var/log/mvt` is mvt:adm with setgid, and the CloudWatch agent's user is in adm, so it reads the product log and nothing under `/var/lib/mvt`. The agent's log group is read from the instance settings with a YAML parser | The Terraform module quotes the settings' keys and CloudFormation does not | Yes |
| 72 | A customer's own KMS key | Its policy stays the customer's. The two statements it needs (CloudWatch Logs, and the instance role where the policy does not delegate to IAM) are in the deployment guide and, for Terraform, the `customer_key_policy_statements` output, to add before deploying | A template cannot change a key policy it does not own, and the log group fails to create without the first statement | Yes |
| 73 | Worked example | The AMI ships `example`, a files only project over two folders in `/opt/mvt/example`, with one changed invoice amount and one line ending change. It runs from the run document or the UI and writes its report to the deployment's bucket | Spec 17: a first result with nothing to set up, which also proves the bucket and key work | Yes |
| 74 | Progress kept in the store | A reconciliation copies each findings segment to the store as it closes, and closes one at least every minute. After a table it checkpoints (at most every 15 seconds) `progress.json`: the finished tables, their segments, the baseline and the sampling seed; a baseline checkpoints its manifest the same way. `--resume` (the newest unfinished run, found through a marker in the store, or `--run-id`) carries on from the checkpoint on any instance, compares only the unfinished tables, and empties in the store the segments written after the checkpoint. A copy that fails is retried at the next checkpoint and never stops the run. The run document has a `resume` parameter | Spec 3, 9.16 and 18: a lost instance costs at most the tables since the last checkpoint, and resuming never counts a finding twice. Against a live source the remaining tables are read as of the resume, and the report says when that was | Yes |
| 75 | What a failed run never reached | A reconciliation that fails names each planned table it had not finished as not checked ("the run stopped before this table was compared"); a `validate` that fails names the file sets and journeys it never reached. Coverage counts them | Spec 12: a run that stopped must not read as one that covered less but finished | Yes |
| 76 | Project files in the store | Every run copies its project file to `<prefix>/project.yaml` and to `.liftproof/projects/<name>.yaml` at the bucket root. `liftproof restore`, run once per instance by `mvt-restore.service` before the scheduler and the UI start, writes back each one missing on the instance and never replaces one that is there. A project whose store is another bucket is not restored | Project files hold secret ARNs, never credentials; the index at the root finds every project whatever its prefix | Yes |
| 77 | Run history and journeys from the store | `liftproof runs`, the UI's run list and its journey list read the store as well as the instance, so runs and journeys recorded on another or a replaced instance appear | Spec 3 and 14 | Yes |
| 78 | Data ranges in the report | Per table and side: the lowest and highest value of the first key column and of each date and time column, over the rows the comparison read (row ignore rules applied), one MIN/MAX statement per table and side; a baseline records its side's when it is taken. Only integer and exact keys and dates by default; text keys only with `show_values`. `database.ranges: false` turns them off | Spec 12 asks for the key and date ranges covered. Ends of a text key (an email address) are row values, which the report holds only on request | Yes |
| 79 | Regenerated reports | `liftproof report --run` keeps the run's range block and run metadata as the run recorded them and adds `regenerated` (when, who, which version). ## Not built yet

SQL Server transactional replication (see 63), and parallel whole snapshot baselines on
MySQL and SQL Server (no shared snapshot; per table they run in parallel, 113). A table
too large to hold a snapshot for gets no help from `snapshot: per_table`: that would take
a snapshot per bucket. doctor does not yet say whether the source is a read replica,
and each table's row count is still a read of its own (see 100): sizing buckets from
catalogue estimates and taking the exact count from the aggregate would save it.
PostgreSQL dates after the year 9999 or before the year 1 (BC), and the time `24:00:00`,
still fail to load (data ranges, JSON tables, drill-down), and the pushdown renders a BC
date without its era and `24:00:00` as midnight; each is a later canonical revision (105).
`time` has no data ranges, so a baseline table older than a `24:00:00` rule cannot be shown
to hold none.
XML (108 to 111): an entity declared only in an external DTD (XHTML `&nbsp;`) has no
canonical form, so its column is not checked; a prefix renamed for the same namespace, a
default namespace against a prefix, and typed XML that an engine writes in its own form
(an XML schema bound column) remain differences; an `xsi:type` value with a character
outside letters, digits and `_` (a hyphen, a dot) is compared as text, not as a qualified
name. A value refused on one side is found after the other side has read the whole table,
which is then read again, and XML tables are canonicalised on one core.

key actions (`ON DELETE`) and deferrability, index direction, the conditions of partial
indexes and the expressions of expression indexes are not compared, nor how a unique key
treats NULL (SQL Server allows one, PostgreSQL `NULLS NOT DISTINCT` none); a MySQL
invisible index counts as there. A target with no secondary index at all gets one finding
per index rather than one for the database.
